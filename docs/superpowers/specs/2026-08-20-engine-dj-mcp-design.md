# Engine DJ MCP — дизайн v1

Дата: 2026-08-20
Статус: на утверждение

## 1. Цель

MCP-сервер, дающий ассистенту доступ к библиотеке Engine DJ (Denon DJ / inMusic).
Два сценария v1: **умный поиск трека** и **аудит коллекции**. Только чтение.

Ниша свободна: Engine DJ MCP не существует ни на GitHub, ни в npm/PyPI, ни в
официальном MCP-реестре, ни на glama/PulseMCP/Smithery. Эталон формы —
`davehenke/rekordbox-mcp` (MIT, Python, 31 инструмент).

Engine DJ технически проще и безопаснее rekordbox: библиотека — обычный
незашифрованный SQLite, тогда как rekordbox требует извлечения ключа SQLCipher.

### Семантика полей

Извлечено из бинарника `Engine DJ` и подтверждено на живой схеме.

- **Тональность.** `Track.key INTEGER` в диапазоне 0–23, `-1` = не определена.
  Преобразование, которое использует само приложение:
  `CASE key WHEN -1 THEN NULL ELSE (key + 15 - 2*(key % 2)) % 24 END`
- **Темп.** Реальное значение — `COALESCE(bpmAnalyzed, bpm)`, где `bpm` хранится
  как целое ×100 (12800 = 128.0), а `bpmAnalyzed` — `REAL`.
- **Путь.** `Track.path` относительный от `Engine Library`, обычно содержит `..`.
- **Плейлисты** — односвязные списки: `Playlist.nextListId`,
  `PlaylistEntity.nextEntityId`. Порядок поддерживается триггерами.
- **Естественный ключ трека** — `(originDatabaseUuid, originTrackId)`,
  есть `UNIQUE`-констрейнт.
- **Анализ.** Тональность определяется библиотекой `zplane::MusicTheory::Key`,
  битгрид — `BeatAnchorCollection` (набор якорей, а не сетка фиксированного шага).

### `lastEditTime` непригоден как watermark

Живой триггер:

```sql
CREATE TRIGGER trigger_after_update_only_Track_timestamp
  AFTER UPDATE OF length, bpm, year, filename, bitrate, bpmAnalyzed, albumArtId,
  title, artist, album, genre, comment, label, composer, remixer, key, rating,
  albumArt, fileType, isAnalyzed, isBeatgridLocked, explicitLyrics
  ON Track ...
```

Не покрывает: `INSERT`, удаления, `path`, `timeLastPlayed`, `isPlayed`,
`playedIndicator`. То есть проигрывание трека и перемещение файла не двигают
`lastEditTime`. Инкрементальная синхронизация на нём молча разойдётся
с реальностью.

Синтетическая библиотека 50 000 треков в реальной схеме 3.0.2.

## 3. Область v1

**Входит:** только чтение; умный поиск; аудит коллекции; чтение и декодирование
`PerformanceData` (кью, лупы, битгрид, сводка волновой формы); произвольный
read-only SQL как escape hatch.

**Не входит:** любая запись; `hm.db` и разбор истории; сборка сет-листа; diff
между дисками; StagelinQ; MCP prompts; схемы 1.x и 2.x.

## 4. Архитектура

### 4.1 Процессы

```
main (MCP-сервер, stdio)
  ├─ IPC ──► query-процесс   долгоживущий, соединение A
  └─ spawn ► sync-процесс    короткоживущий, соединение B
```

**query-процесс.** Обслуживает все запросы к библиотеке. Холодный старт 40 мс,
запрос 1 мс. Умирает по таймауту (`SIGKILL`), по собственному сбою или по
простою; поднимается лениво на следующем запросе.

Отдельный процесс нужен по двум причинам, обе проверены:

1. **`node:sqlite` невозможно прервать.** В API нет `interrupt()`, а `DatabaseSync`
   синхронный: тяжёлый self-JOIN на 50k блокирует event loop на 2.2 с.
   `worker.terminate()` **не спасает** — вернулся через 1928 мс, то есть дождался
   конца запроса; прервать синхронный нативный вызов он не может.
   `fork()` + `SIGKILL` убивает процесс за 2 мс.
2. **`node:sqlite` помечен экспериментальным.** Сбой на некорректном BLOB'е
   убьёт изолированный процесс, а не MCP-сервер.

**sync-процесс.** Пересобирает индекс и завершается. Живёт около 104 мс.

### 4.2 Соединения

```
Соединение A (query — сюда ходит модель)
  main   = m.db          readOnly: true      ← гарантия уровня ядра
  ATTACH   sidecar.db    ?mode=ro

Соединение B (sync — только наш код)
  main   = sidecar.db    writable
  ATTACH   m.db          ?mode=ro
```

Инверсия принципиальна. Если основным сделать sidecar, а `m.db` подключить в
`?mode=ro`, модель может выполнить `ATTACH '<путь к m.db>' AS rw` уже без
`mode=ro` и писать в библиотеку — **проверено, проходит**.

Когда `m.db` является основной БД соединения и открыта `readOnly`, ограничение —
свойство дескриптора, а не PRAGMA. Проверено на этой топологии:

| Вектор | Результат |
|---|---|
| повторный `ATTACH` той же БД + запись | `SQL logic error` |
| `WITH ... INSERT` | `attempt to write a readonly database` |
| несколько стейтментов через `;` | `prepare()` игнорирует всё после первой `;` |
| `PRAGMA journal_mode=WAL` на attached | `attempt to write a readonly database` |
| `load_extension()` | `SQL logic error` |
| `VACUUM INTO` | **проходит на уровне ядра** → блокируется гардом на ведущий стейтмент |

`PRAGMA query_only=ON` рассматривался и отвергнут: он блокирует всё
перечисленное, но **снимается обратно из SQL**, то есть модель разблокирует себя
сама.

### 4.3 Sidecar

Расположение: `~/.engine-dj-mcp/<library-uuid>/index.db`, отдельный каталог на
каждую библиотеку (ключ — `Information.uuid`).

| Таблица | Содержимое |
|---|---|
| `fts_track` | FTS5 по `title, artist, album, genre, comment, label`, токенайзер `unicode61 remove_diacritics 2` |
| `fts_map` | `rowid` → `track_id` |
| `track_derived` | `track_id`, `camelot`, `tempo`, `has_cues`, `has_grid`; индексы по `camelot` и `tempo` |
| `index_meta` | `library_uuid`, `schema_version`, `change_counter`, `built_at`, `generation` |

Даёт четыре вещи, которых нет в самой Engine: полнотекстовый поиск с
нормализацией диакритики, индексируемые производные поля, место под собственные
данные без единого байта в чужой БД, и полное отсутствие файлов `-journal` рядом
с библиотекой пользователя.

Диакритика существенна: Engine ищет только через `LIKE` и промахивается по
`Björk`, `Röyksopp`, `Ämbient`. Проверено — FTS5 с этим токенайзером находит.

### 4.4 Слои

| Слой | Ответственность |
|---|---|
| `discovery` | Поиск библиотек, чтение `Information`, allowlist версий |
| `store` | Соединения, ATTACH, пересборка, поколения индекса |
| `semantics` | SQL-функции и производные колонки |
| `blobs` | Декодеры `PerformanceData` |
| `tools` | Поверхность MCP |
| `proc` | Жизненный цикл процессов, таймауты, IPC |

Слой `store` держится тонким намеренно: если `node:sqlite` начнёт меняться,
замена на `better-sqlite3` должна стоить один файл.

## 5. Поверхность MCP

Семь инструментов и два ресурса. Малое число — осознанное решение: описания всех
инструментов висят в контексте на каждом запросе.

### 5.1 Ресурсы

**`engine://schema`** — DDL плюс семантическая шпаргалка: устройство
`key INTEGER`, правило `COALESCE(bpmAnalyzed, bpm)`, относительность `path`,
связные списки плейлистов, перечень SQL-функций и **явное указание использовать
`side.track_derived.camelot` вместо вызова функции в `WHERE`**.

**`engine://libraries`** — найденные библиотеки: путь, `uuid`, версия схемы,
число треков, состояние индекса.

Дублирование с инструментом `list_libraries()` намеренное: не все MCP-клиенты
подтягивают ресурсы, а без списка библиотек сервер невозможно диагностировать.
Ресурс отдаёт снимок на момент старта, инструмент — актуальное состояние.

### 5.2 Инструменты

```ts
search_tracks({
  q?:      string      // FTS5
  bpm?:    { min?, max?, around?, tolerance_pct? }
  key?:    { camelot?: string[], compatible_with?: string, mode?: 'major'|'minor' }
  rating?: { min?, max? }
  played?: { never?: boolean, before?: string, after?: string }
  added?:  { before?: string, after?: string }
  flags?:  { analyzed?, has_cues?, has_beatgrid?, available? }
  fields?: string[]           // проекция; по умолчанию 6 полей
  limit?:  number             // default 25, max 200
  cursor?: string             // непрозрачный, кодирует (rank, rowid)
  include_total?: boolean     // default false
}) -> { tracks[], total?, next_cursor? }

get_tracks({ ids: number[], fields? })   -> { tracks[] }
get_track_performance({ id })            -> { cues, loops, beatgrid, waveform_summary }
audit_library({ checks?: string[] })     -> { checks: { name, count, sample_ids[] }[] }
run_sql({ sql, params?, limit? })        -> { columns[], rows[], truncated }
list_libraries()                         -> { libraries[] }
refresh_index()                          -> { indexed, elapsed_ms, generation }
```

Все семь — `readOnlyHint: true`, включая `run_sql`; это следствие топологии,
а не декларация. Все имеют `outputSchema` и возвращают `structuredContent`.

Форматы и семантика параметров:

- Даты (`played.before`, `added.after`) принимают ISO-8601 (`2026-01-15`) либо
  относительный модификатор SQLite (`-6 months`, `-30 days`).
- `bpm.around` с `tolerance_pct` раскрывается в диапазон
  `[around * (1 - p/100), around * (1 + p/100)]`; `tolerance_pct` по умолчанию 3.
- `key.compatible_with: "8A"` возвращает соседей по кругу Camelot: тот же номер
  в другом ладу (`8B`), плюс-минус один номер в том же ладу (`7A`, `9A`).
- `key.camelot` — точный список меток, объединяется с `compatible_with` через OR.

Пример разбора запроса «что-то тёмное на 124 в миноре, что я давно не играл»:

```
q: "dark", bpm: { around: 124, tolerance_pct: 3 },
key: { mode: "minor" }, played: { before: "-6 months" }
```

`played.before` опирается на `timeLastPlayed`, по которому в самом Engine
фильтровать нельзя.

### 5.3 Токен-экономия

- **Проекция по умолчанию** — `id, artist, title, bpm, camelot, rating`:
  шесть полей из сорока трёх.
- **Курсор вместо offset.** Составной `(rank, rowid)` при
  `ORDER BY rank, f.rowid`. Keyset по одному `id` **невозможен**: при сортировке
  по релевантности идентификаторы немонотонны (проверено: 615, 1171, 1727).
- **Потолок.** `limit` по умолчанию 25, максимум 200.
- **`total` по требованию.** Стоит ×18.8 к цене страницы (3.3 мс против 0.2 мс).
  По умолчанию выключен; при включении считается с потолком
  (`LIMIT 1001` → `1000+`).
- **Агрегаты на сервере.** `audit_library` возвращает счётчик и до десяти
  примеров, а не строки.
- **Волновая форма никогда не отдаётся сырой** — только `waveform_summary`:
  длительность, число пиков, огрублённый профиль энергии.

### 5.4 SQL-функции

Регистрируются на соединении A, все `deterministic`.

| Функция | Назначение |
|---|---|
| `camelot(key)` | `key INTEGER` → метка круга Camelot |
| `key_name(key)` | привычная нотация (`Am`) |
| `tempo(bpmAnalyzed, bpm)` | правило Engine |
| `key_distance(a, b)` | расстояние по кругу Camelot |
| `abs_path(path)` | относительный путь → абсолютный |

**Важно:** JS-функция в `WHERE` вызывается на каждой строке и убивает индекс.
Измерено на 50k: `camelot(key)` в `WHERE` — 4.3 мс (полный скан),
индексированный `track_derived.camelot` — 0.06 мс, то есть ×72. Поэтому функции —
escape hatch для разовых запросов, а канонический путь для фильтрации по
тональности и темпу — `side.track_derived`.

### 5.5 Проверки `audit_library`

Все выведены из реальной схемы.

```
missing_files    файла по path нет на диске
unavailable      isAvailable = 0
unanalyzed       isAnalyzed = 0
no_cues          quickCues пуст или NULL
no_beatgrid      beatData пуст или NULL
missing_key      key = -1
suspicious_bpm   |bpmAnalyzed - bpm/100| > 1.0 либо темп вне диапазона 60..200
duplicates       нормализованные (artist,title); отдельно (fileBytes,length)
empty_metadata   нет artist или title
orphan_entries   PlaylistEntity ссылается на несуществующий Track
```

## 6. Поток данных

### 6.1 Обнаружение

Проверяются: `~/Music/Engine Library/Database2/m.db` и та же структура на всех
смонтированных томах. Для каждой найденной — чтение `Information` через
`SELECT *` с защитным разбором (набор колонок может отличаться между версиями).

### 6.2 Пересборка вместо синхронизации

Инкрементального синка нет. Причины: `lastEditTime` ненадёжен (см. 2), а честный
change-probe стоит 52 мс при полной пересборке в 104 мс — экономить нечего.

Уходит целый класс багов: рассинхрон, дрейф, «удалённый трек остался в индексе»,
логика инвалидации.

### 6.3 Проба устаревания

**Счётчик изменений из заголовка SQLite** — 4 байта big-endian по смещению 24
файла `m.db`. Инкрементируется на каждой пишущей транзакции, является частью
формата файла, переживает перезапуск процесса. Стоимость — 0.030 мс.

`mtime + size` отвергнуты: при восстановлении, сохраняющем mtime (`rsync -t`,
Dropbox, Time Machine, Engine DJ Cloud), изменение содержимого **не
обнаруживается**, и индекс устаревает навсегда. Проверено: `mtime` и `size`
неизменны, счётчик 13 → 14.

`PRAGMA data_version` отвергнут: в двух свежих соединениях возвращает одно и то
же значение, отслеживает изменения только в пределах жизни соединения.

### 6.4 Публикация индекса

Пересборка идёт во временный файл, затем `rename()`. **Одного `rename()`
недостаточно:** открытое соединение продолжает читать старый inode и молча
отдавать устаревшие данные (проверено — после подмены запрос вернул «СТАРЫЙ»).

Поэтому после успешной пересборки sync-процесс сообщает main'у новое поколение
индекса, main передаёт его query-процессу, тот выполняет
`DETACH side; ATTACH side`.

## 7. Обработка ошибок

Все — структурированный результат, не исключение. Исключения остаются только для
ошибок программиста: стек-трейс в ответе инструмента отравляет контекст,
а `{"error": "library_busy", "retry_after_ms": 5000}` модель отрабатывает
корректно с первого раза.

```
library_busy           Engine DJ пишет в библиотеку; retry_after_ms
library_not_found      папка Engine Library не найдена
unsupported_schema     версия вне allowlist; в detail — найденная версия
query_timeout          запрос убит по таймауту; в detail — EXPLAIN QUERY PLAN
query_process_crashed  процесс упал и поднят заново
index_stale            индекс устарел: БД была занята при пересборке
decode_failed          BLOB не разобран (внутри get_track_performance)
```

**`library_busy`.** На соединении A `busy_timeout = 3000` плюс три попытки
с джиттером. Sync-процесс не ждёт вообще: отменяет пересборку и отдаёт прошлый
индекс с флагом `index_stale`. Поиск при работающем Engine DJ должен работать
всегда, пусть по слегка устаревшему индексу.

**`query_timeout`.** Единственная реальная защита от тяжёлого запроса —
`SIGKILL`. `EXPLAIN QUERY PLAN` **не используется как ворота**: проверенная
эвристика даёт либо ложные срабатывания на легитимных запросах (наивное правило
блокирует и FTS-поиск, и `GROUP BY`), либо, в уточнённом виде, пропускает
тройное декартово произведение. План запроса включается в текст ошибки как
диагностика.

**`unsupported_schema`.** Allowlist точных версий:

| Версия | v1 |
|---|---|
| `3.0.0`–`3.0.2` | поддержана |
| `2.x` | отказ (читаема в принципе — `PerformanceData` там VIEW с теми же колонками — но не проверена) |
| `1.x` | отказ (модель данных EAV) |
| новее известного | отказ, без угадывания |

`list_libraries()` работает **всегда**, включая неподдерживаемые версии:
пользователь должен видеть «схема 3.1.0, не поддерживается», а не пустой список.

## 8. Декодирование `PerformanceData`

> **Раздел требует валидации на реальной библиотеке.** Всё ниже основано на
> анализе бинарника и на стороннем коде, но ни разу не проверено на живых байтах,
> потому что тестовая библиотека пуста.

Колонки: `trackData`, `overviewWaveFormData`, `beatData`, `quickCues`, `loops`,
`activeOnLoadLoops`.

Ожидаемое кодирование — Qt `qCompress`: 4 байта big-endian длины плюс сырой zlib.
Известные ловушки, которые нужно подтвердить: `beatData` со смешанным порядком
байт (заголовок big-endian, маркеры little-endian, 24 байта на маркер),
`quickCues` целиком big-endian, `loops` без сжатия и little-endian. Позиции
измеряются в сэмплах, не в секундах; частота дискретизации лежит в `trackData`.

Ориентир для порта — `jrgutier/rb2engine` (Python, MIT, есть golden-фикстуры от
реального Engine) и `xsco/libdjinterop` (C++, LGPL) как спецификация формата.
libdjinterop не линкуется и не биндится — используется только как описание.

**Контракт декодеров: они никогда не бросают исключений.** Каждое поле
возвращает свой статус:

```json
{ "cues":     { "status": "ok", "items": [...] },
  "beatgrid": { "status": "unsupported",
                "detail": "неизвестная сигнатура заголовка 0x03", "bytes": 412 },
  "waveform_summary": { "status": "corrupt", "detail": "zlib: incorrect data check" } }
```

Сбой декодера не имеет права ломать ничего вокруг: трек с неразобранным
`beatData` находится поиском, попадает в аудит и отдаёт свои кью, если они
разобрались. Форматы реверс-инженерены, поэтому встретить неизвестное — норма.
Неизвестные сигнатуры и длины пишутся в лог: это бесплатная телеметрия о том,
какие варианты существуют в природе.

## 9. Безопасность и границы

- Библиотека пользователя открывается только read-only, гарантия уровня ядра.
- Ни одного файла не создаётся рядом с `Database2/` (проверено).
- Гард на ведущий стейтмент в `run_sql`: отказ на `VACUUM`, `ATTACH`, `DETACH`.
  Читающие `PRAGMA` (`table_info`, `table_list`, `index_list`) разрешены — они
  полезны модели для интроспекции, а пишущие всё равно отбиваются ядром.
  Гард осмыслен, потому что `prepare()` игнорирует всё после первой `;`
  (проверено) — склеить два запроса в один вызов нельзя.
- `enableLoadExtension` не включается никогда.
- **Приватность.** `filename`, `uri`, `comment`, `timeLastPlayed`, `isPlayed`,
  `playedIndicator`, `streamingSource` — поведенческий профиль. Абсолютные пути
  содержат имя пользователя. Предусмотреть режим редакции путей; историю
  прослушиваний не включать в проекцию по умолчанию.

## 10. Тестирование

За три прохода дизайна тестами найдено семь ошибок, ни одна из которых не
выявлялась рассуждением. Поэтому тесты здесь — несущая конструкция, а не
формальность.

### 10.1 Регрессионный набор из найденных ошибок

Каждая находка становится постоянным тестом:

1. `ATTACH` той же БД без `mode=ro` с последующей записью → отказ.
2. `WITH ... INSERT` → отказ.
3. `VACUUM INTO` → отказ гарда.
4. Несколько стейтментов через `;` → выполняется только первый.
5. Изменение содержимого при сохранённом `mtime` → проба обнаруживает.
6. Курсор при `ORDER BY rank` → страницы не пересекаются и ничего не теряют.
7. Тяжёлый запрос → убит по таймауту, процесс поднят, следующий запрос работает.
8. Фильтр по тональности использует индекс `track_derived`, а не скан.
9. Подмена индекса → после переподключения видны новые данные.

### 10.2 Прочее

- **Golden-фикстуры BLOB'ов** — байты из реальной библиотеки плюс ожидаемый
  разбор. Появятся после получения библиотеки.
- **Синтетический генератор** библиотеки в схеме 3.0.2 — уже написан, даёт 50k
  треков за 0.5 с; используется для тестов производительности в CI.
- **Устойчивость декодеров** — подача мусора, обрезанных и пустых BLOB'ов;
  проверка, что возвращается статус, а не исключение.
- **Бюджеты производительности в CI** на синтетических 50k: пересборка < 300 мс,
  страница поиска < 5 мс, проба < 1 мс.

## 11. Дистрибуция, имя, лицензия

**Имя:** `engine-dj-mcp`. Номинативное добросовестное использование; в шапке
README — явный дисклеймер о неаффилированности с inMusic / Denon DJ. Логотипы и
фирменная графика не используются.

**Лицензия:** MIT. Совместима с экосистемой; `rb2engine` (источник ориентира по
BLOB'ам) — тоже MIT, при портировании указывается атрибуция. `libdjinterop`
(LGPL) не линкуется, используется только как описание формата.

**Дистрибуция:** npm с запуском через `npx engine-dj-mcp`, плюс сборка Desktop
Extension. Целевая аудитория — диджеи, а не разработчики, поэтому установка не
должна требовать рантайма. Отсюда же выбор `node:sqlite`: ноль нативных
зависимостей.

**Правовой фон.** EULA inMusic §3.2 запрещает реверс-инжиниринг *программы*, а
не чтение файлов данных; технических мер защиты, которые можно было бы обходить,
здесь нет. inMusic публикует статью для сторонних разработчиков с контактом
`developers@enginedj.com`. Публичных претензий к `libdjinterop` (существует
с 2017 года, упакован в Debian/Ubuntu/FreeBSD) или к Mixxx, отгружающему
Engine-экспорт, не зафиксировано.

## 12. Открытые вопросы

Блокируются отсутствием реальной библиотеки (ожидается 2026-08-21):

1. **Семантика `camelot()`.** Формула взята из бинарника и корректна как
   перестановка, но что означает результат `19` как метка круга — неизвестно.
   Нужен один трек с известной тональностью для привязки нумерации.
2. **Форматы BLOB'ов** — сигнатуры, порядок байт, размеры записей на живых
   данных.
3. **Стоимость декодирования** на 50k. В синтетике BLOB'ы — пустышки.
4. **`missing_files` на внешнем диске.** 99 мс — локальный SSD и быстрый путь
   «файла нет». По USB с реально существующими файлами будет на порядки
   медленнее; понадобится прогресс и кэш по mtime.

Не блокирующее:

5. Письмо на `developers@enginedj.com` про использование имени. Стоит ноль,
   снижает риск сильнее всего остального.
